## 12.2.1 Why a Constraint System at All

The naive approach — grab 200 phrases, run them through the scorecard, done — falls apart in three ways once you're actually cycling LoRAs weekly:

1. **Phoneme drift.** The pool skews toward whatever phrases were easy to write. If 60% of the bank is heavy on `/s/` and `/t/`, a LoRA that mangles bilabials `/p/ /b/ /m/` scores fine and gets promoted. Two weeks later, real prompts hit those bilabials and the LoRA visibly fails.

2. **Length collapse.** Writers gravitate to a comfortable sentence length (typically 8–12 words). SyncNet behavior on 3-word barks versus 30-word monologues is genuinely different — long phrases forgive small drift, short ones don't. Without an explicit length distribution, you're only ever testing one regime.

3. **Emotional monoculture.** Neutral declaratives are cheap to write. Whisper, shout, choked-back, breathy, wet — all the phonation modes that stress an audio-reactive LoRA hardest — get underrepresented. A LoRA that can only do "podcast voice" ships to prod and everyone wonders why the moaning scenes look like a ventriloquist dummy.

The constraint system in `curator.yaml` treats phrase selection as an **integer programming problem**: given a pool of N candidate phrases each tagged with phonemes, length bucket, register, and content class, select a subset of K phrases that satisfies distribution targets on every axis simultaneously. The solver runs weekly, before the frozen bank gets handed to `scorecard.py`.

## 12.2.2 The Config File — Full `curator.yaml`

```yaml
# D:\AI\ComfyUI_portable\workshop\scrape\phrase_bank\config\curator.yaml
# ---------------------------------------------------------------------------
# Balancing constraints for phrase_bank curation.
# Consumed by curator.py; validated on load by curator._validate_config().
# ---------------------------------------------------------------------------

version: 3
updated: "2026-09-21"
updated_by: "workshop"

# --- global sizing --------------------------------------------------------

bank:
  target_size:       240     # phrases in the active bank
  min_size:          200     # solver fails hard below this
  max_size:          280     # solver refuses to inflate beyond this
  frozen_snapshots:  8       # how many historical banks to keep on disk
  rotation_overlap:  0.35    # fraction of prior bank that must survive to next
                             # (prevents week-over-week score discontinuity)

# --- phoneme coverage -----------------------------------------------------
# Each phoneme class has a min/max fraction of the total bank.
# The solver treats these as HARD constraints — infeasibility aborts.
# Values are ARPABET-family collapsed classes; see phoneme_targets.yaml
# for the granular mapping.

phoneme_coverage:
  bilabial_stops:       {min: 0.10, max: 0.18}   # /p/ /b/
  bilabial_nasal:       {min: 0.06, max: 0.12}   # /m/
  labiodental:          {min: 0.05, max: 0.10}   # /f/ /v/
  dental:               {min: 0.04, max: 0.09}   # /θ/ /ð/
  alveolar_stops:       {min: 0.12, max: 0.20}   # /t/ /d/
  alveolar_fric:        {min: 0.14, max: 0.22}   # /s/ /z/
  postalveolar:         {min: 0.06, max: 0.12}   # /ʃ/ /ʒ/ /tʃ/ /dʒ/
  velar:                {min: 0.08, max: 0.14}   # /k/ /g/ /ŋ/
  glottal:              {min: 0.03, max: 0.08}   # /h/ /ʔ/
  liquids:              {min: 0.08, max: 0.15}   # /l/ /r/
  glides:               {min: 0.05, max: 0.10}   # /w/ /j/
  # vowel classes tracked separately — jaw aperture matters for lip-sync
  vowel_open:           {min: 0.18, max: 0.28}   # /a/ /ɑ/ /æ/
  vowel_mid:            {min: 0.22, max: 0.32}
  vowel_close:          {min: 0.18, max: 0.28}   # /i/ /u/
  diphthong:            {min: 0.08, max: 0.16}

# --- length distribution --------------------------------------------------
# Word-count buckets. Every bucket must be non-empty; solver enforces.

length_buckets:
  micro:   {words: [1, 3],   min: 0.08, max: 0.15, priority: high}
  short:   {words: [4, 7],   min: 0.18, max: 0.28, priority: high}
  medium:  {words: [8, 14],  min: 0.28, max: 0.40, priority: normal}
  long:    {words: [15, 25], min: 0.15, max: 0.25, priority: normal}
  epic:    {words: [26, 40], min: 0.05, max: 0.12, priority: low}

# --- register / phonation mode -------------------------------------------
# The single most important axis for NSFW audio-reactive LoRA quality.
# Undersampling any of these silently ships broken LoRAs to prod.

register:
  neutral_declarative:   {min: 0.15, max: 0.25}
  whisper:               {min: 0.08, max: 0.14}
  breathy:               {min: 0.10, max: 0.16}
  moan_soft:             {min: 0.10, max: 0.16}
  moan_loud:             {min: 0.08, max: 0.14}
  gasp_short:            {min: 0.06, max: 0.12}
  shout:                 {min: 0.05, max: 0.10}
  choked:                {min: 0.04, max: 0.09}
  wet_mouthed:           {min: 0.05, max: 0.10}   # saliva/wet consonants
  laugh_giggle:          {min: 0.03, max: 0.07}
  sob_cry:               {min: 0.03, max: 0.07}

# --- content class --------------------------------------------------------
# Semantic buckets. Not correlated with register — a whisper can be
# clinical or filthy. Solver optimizes across both axes independently.

content_class:
  clinical_neutral:      {min: 0.08, max: 0.16}   # "the subject rotated"
  conversational:        {min: 0.15, max: 0.25}
  narrative_prose:       {min: 0.12, max: 0.20}
  dirty_talk_soft:       {min: 0.10, max: 0.18}
  dirty_talk_explicit:   {min: 0.12, max: 0.22}
  commanding:            {min: 0.06, max: 0.12}
  submissive:            {min: 0.06, max: 0.12}
  degradation:           {min: 0.04, max: 0.10}
  praise_affirming:      {min: 0.05, max: 0.10}
  crude_slang:           {min: 0.05, max: 0.12}

# --- cross-axis constraints -----------------------------------------------
# These catch degenerate solutions where individual axes look balanced
# but the joint distribution is broken (e.g. all "whisper" phrases are
# also "clinical_neutral" — technically legal, useless in practice).

cross_axis:
  - name: "register x content — no monoculture pairs"
    rule: "for_each_pair(register, content_class): count <= 0.08 * bank.target_size"

  - name: "register x length — whispers not all micro"
    rule: "count(register=whisper, length=micro) <= 0.30 * count(register=whisper)"

  - name: "explicit content spread across registers"
    rule: "count(content=dirty_talk_explicit, register in [whisper,breathy,moan_soft,moan_loud]) >= 0.60 * count(content=dirty_talk_explicit)"

  - name: "bilabial stress across lengths"
    rule: "count(phoneme=bilabial_stops, length in [short,medium,long]) >= 0.70 * count(phoneme=bilabial_stops)"

# --- rotation policy ------------------------------------------------------
# How the bank churns week-over-week.

rotation:
  max_phrase_age_cycles:      12    # a phrase in bank > 12 weeks gets forced-retired
  min_phrase_dwell_cycles:    2     # a fresh phrase must survive >= 2 cycles before eligible for retire
  retire_score_threshold:     0.35  # phrases whose composite discriminative score drops below this get retired
  keep_high_discriminators:   true  # never retire top 10% by discriminative score, even if age exceeds max
  new_phrase_quota_min:       0.15  # at least 15% of each new bank must be phrases not present in prior bank
  new_phrase_quota_max:       0.40  # cap on churn to preserve score continuity

# --- discriminative scoring -----------------------------------------------
# Phrases that don't separate good LoRAs from bad ones are dead weight.
# The curator tracks per-phrase variance across LoRAs scored on it.

discrimination:
  min_loras_before_scoring: 8       # need at least 8 LoRA runs to score a phrase
  variance_metric:          "syncnet_offset_stddev"   # cross-LoRA stddev of primary metric
  weight_in_selection:      0.25    # tie-breaker weight, not primary axis

# --- solver -----------------------------------------------------------------

solver:
  backend:              "cp_sat"    # google or-tools CP-SAT
  time_limit_seconds:   45          # hard wallclock cap; solver returns best-so-far
  num_workers:          6           # parallel search threads (5090 box has plenty)
  random_seed:          20260921    # deterministic across reruns
  objective_weights:
    coverage_slack:     1.0         # minimize distance from bucket midpoints
    discrimination:     0.25        # prefer high-discrimination phrases
    novelty:            0.15        # slight bias toward phrases with low prior-bank overlap
    age_penalty:        0.10        # mild pressure to churn oldest phrases

# --- failure handling -----------------------------------------------------

on_infeasible:
  # If the solver proves infeasibility, relax in this order until sat.
  relaxation_order:
    - "cross_axis"                  # relax cross-axis first (soften to warn-only)
    - "content_class"               # then content bounds by ±25%
    - "register"                    # then register bounds by ±20%
    - "length_buckets"              # then length bounds by ±15%
    - "phoneme_coverage"            # phoneme is the last thing to bend
  max_relaxation_rounds: 4
  abort_if_still_infeasible: true   # emit sentinel, page operator
  operator_email: "${PIPELINE_OPERATOR_EMAIL}"
  event_source:   "ComfyUI-Curator"
  event_id_infeasible: 9100
```

## 12.2.3 Constraint Semantics — What the Solver Actually Sees

Each phrase in `phrase_pool.jsonl` carries tags like:

```json
{
  "id": "p_00841",
  "text": "Fuck, you feel so goddamn tight, don't stop.",
  "words": 9,
  "length_bucket": "medium",
  "phonemes": ["labiodental","velar","alveolar_fric","vowel_open",
               "alveolar_stops","alveolar_fric","alveolar_stops",
               "vowel_mid","bilabial_stops","alveolar_stops"],
  "register": "moan_loud",
  "content_class": "dirty_talk_explicit",
  "age_cycles": 3,
  "discriminative_score": 0.62,
  "prior_bank_member": true
}
```

The solver builds one binary decision variable `x_i ∈ {0,1}` per candidate phrase. Constraints translate to linear inequalities over sums of those variables:

| YAML section | Constraint form |
| --- | --- |
| `bank.target_size` | `Σ x_i == 240` (with slack ±20 via `min_size`/`max_size`) |
| `phoneme_coverage.bilabial_stops.min` | `Σ x_i · has_phoneme(i, bilabial_stops) >= 0.10 · Σ x_i` |
| `length_buckets.short.max` | `Σ x_i · in_bucket(i, short) <= 0.28 · Σ x_i` |
| `register.whisper.min` | `Σ x_i · reg(i)==whisper >= 0.08 · Σ x_i` |
| `content_class.dirty_talk_explicit.min` | `Σ x_i · cls(i)==dirty_explicit >= 0.12 · Σ x_i` |
| `cross_axis` (pair caps) | `Σ x_i · (reg(i)==r ∧ cls(i)==c) <= 0.08 · 240` for each (r,c) pair |
| `rotation.new_phrase_quota_min` | `Σ x_i · ¬prior_bank_member(i) >= 0.15 · Σ x_i` |
| `rotation.max_phrase_age_cycles` | `x_i == 0` for all i where `age_cycles(i) > 12` unless in top-decile discriminator set |

The **objective** is a weighted sum of four scalar terms, all normalized to `[0,1]`:

```txt
minimize:
    w_slack       · Σ_axis Σ_bucket |frac(bucket) - midpoint(bucket)|
  − w_disc        · Σ x_i · discriminative_score(i) / target_size
  − w_novelty     · Σ x_i · (1 - prior_bank_member(i)) / target_size
  + w_age_penalty · Σ x_i · age_cycles(i) / (max_age · target_size)
```

The slack term is the primary driver — it pulls each bucket toward the midpoint of its min/max range, so a phrase distribution ends up centered rather than pinned to a boundary where next week's minor pool changes could flip feasibility.

## 12.2.4 The Cross-Axis Rule DSL

The `cross_axis[].rule` strings are parsed by a tiny domain-specific evaluator in `curator.py` (Part 12.3). Grammar:

```txt
rule       := clause (op clause)?
clause     := "count" "(" filters ")" bound
filters    := filter ("," filter)*
filter     := axis "=" value | axis "in" "[" value ("," value)* "]"
bound      := ("<=" | ">=" | "==") expr
expr       := number ("*" identifier ("." identifier)*)?
op         := "and" | "or"
for_each   := "for_each_pair" "(" axis "," axis ")" ":" clause
```

Legal axes: `phoneme`, `length`, `register`, `content`. The evaluator compiles each rule to a lambda over `(bank_selection, config)` returning a bool + slack magnitude. Rules that reference `bank.target_size` resolve at parse time; rules that reference selection counts (`count(register=whisper)`) resolve during solve.

Two examples fully expanded:

```txt
"count(register=whisper, length=micro) <= 0.30 * count(register=whisper)"
```

Solver adds: `Σ x_i·[reg==whisper ∧ len==micro] − 0.30 · Σ x_i·[reg==whisper] <= 0`

```txt
"for_each_pair(register, content_class): count <= 0.08 * bank.target_size"
```

Expands at parse time into `|R| × |C| = 11 × 10 = 110` separate constraints, one per (register, content) pair, each bounding that pair's phrase count at `0.08 × 240 = 19.2 → 19`.

## 12.2.5 Infeasibility Handling — The Relaxation Ladder

When the pool doesn't contain enough phrases satisfying every constraint simultaneously — typical after a burst of new-phrase intake that skews toward one register — the solver returns `INFEASIBLE`. Rather than fail hard, `curator.py` walks `on_infeasible.relaxation_order` and retries:

```txt
Round 0: solve with all constraints as-is
    → INFEASIBLE
Round 1: demote cross_axis rules from HARD to soft (add to objective as penalty)
    → still INFEASIBLE
Round 2: widen content_class bounds by ±25%
    → SAT, but with logged warning
Round 3: (not reached)
```

Each round emits a structured log entry:

```txt
2026-09-21T08:00:14Z WARN curator round=2 relaxed=content_class
  original_bounds={"dirty_talk_explicit": [0.12, 0.22]}
  relaxed_bounds ={"dirty_talk_explicit": [0.09, 0.275]}
  reason="pool insufficient explicit phrases in target length buckets"
```

If all four relaxation rounds fail, `curator.py` writes a sentinel at `phrase_bank/curator.blocked` containing the last solver stats, sends the operator email, writes EventLog ID `9100`, and exits `4`. The daily promotion job in `promote_trigger.ps1` treats that sentinel the same way it treats the lock-doctor sentinel from Part 9 — the pipeline halts until an operator clears it.

The `relaxation_order` is deliberately ordered from **least damaging to most damaging**. Cross-axis rules are the softest safety net; loosening them means "the bank might have some register/content monocultures this week, but at least it exists." Phoneme coverage is at the bottom because a bank with broken phoneme balance actively lies about LoRA quality — better to halt the pipeline than to ship a compromised measurement.

## 12.2.6 Failure Modes

| # | Failure | Symptom | Detection | Recovery |
| --- | --- | --- | --- | --- |
| C1 | Pool too small for target_size | Solver returns INFEASIBLE round 0 | `pool_size < 2.5 × target_size` check before solve | Force intake of new phrases via `phrase_intake.py` (Part 12.4) before rerun |
| C2 | One register class has zero pool members | Solver returns INFEASIBLE, all four rounds fail | Pre-solve pool audit logs empty registers | Sentinel written; operator adds phrases manually |
| C3 | YAML syntax error | `curator.py` fails at load | Schema validation on load | Config not applied; last-known-good remains in effect |
| C4 | Cross-axis rule references unknown axis | Parse-time exception | DSL parser validates axis names against schema | Rule ignored, WARN logged, solve continues |
| C5 | Solver hits time_limit_seconds without proving optimality | Returns best-so-far solution | `solver_stats.status == FEASIBLE` (not `OPTIMAL`) | Accepted with WARN; bump `time_limit_seconds` if recurrent |
| C6 | Rotation overlap constraint conflicts with new_phrase_quota_min | Round 0 infeasible even on well-stocked pool | Pre-solve arithmetic check: `overlap + quota_min <= 1.0` | Config validator rejects load; operator adjusts YAML |
| C7 | Discriminative scores stale (no LoRA runs in >30 days) | Objective weight silently no-ops | `curator.py` warns if `max(score_age) > 30 days` | Trigger a rescore pass via `scorecard.py --rescore-all` |
| C8 | Phoneme tagger drift (upstream tagger changes ARPABET mapping) | Coverage constraints suddenly infeasible en masse | Diff current pool's phoneme distribution vs prior week | Roll back tagger version; re-tag pool |
| C9 | Frozen snapshot missing during rotation calc | `prior_bank_member` all false → new_phrase_quota trivially satisfied | Rotation module checks `phrase_bank_frozen.jsonl` mtime | Fall back to last available frozen; log WARN |
| C10 | Age counter not incremented (cron miss) | Rotation stops churning; stale phrases pile up | `age_cycles` distribution monitor in curator log | Manual `curator.py --tick-ages` to catch up |

## 12.2.7 Runbook — Editing `curator.yaml` Safely

`curator.yaml` is the tuning surface for the entire phrase bank. A bad edit doesn't crash the pipeline — it silently reshapes the corpus, and you don't notice until three weeks later when the voice LoRA starts mispronouncing sibilants because you accidentally starved the /s/ bucket. This runbook exists so that never happens.

---

### Step 0 — Prerequisites

Before you touch the file, confirm:

- The latest nightly `curator.py --dry-run` report is green (no infeasibility warnings).
- `phrase_bank.jsonl` has been sealed by `verify_ledger.py --rolling 500` within the last 24h.
- No `promote.py` job is currently running (`Get-Process python | Where-Object CommandLine -like "*promote*"` returns empty).
- You have a shell open at `D:\AI\ComfyUI_portable\workshop\scrape\phrases\`.

If any of those fail, stop. Fix the prerequisite first. Editing `curator.yaml` on top of an unsealed ledger means your rollback point is fictional.

---

### Step 1 — Snapshot the current state

```powershell
$stamp = Get-Date -Format "yyyy-MM-dd_HHmm"
Copy-Item .\config\curator.yaml ".\config\_backups\curator.yaml.$stamp.bak"
python .\curator.py --dry-run --report-out ".\reports\pre-edit.$stamp.json"
```

Two artifacts land on disk: the raw YAML backup and a full pre-edit constraint report. The report is what you'll diff against after the change. Without it you're editing blind — you can *see* the new numbers but not what they displaced.

---

### Step 2 — Edit in a scratch copy, never in place

```powershell
Copy-Item .\config\curator.yaml .\config\curator.yaml.wip
notepad .\config\curator.yaml.wip
```

Editing `curator.yaml` directly is the single most common cause of half-committed states. If the editor crashes or you Ctrl-S at the wrong moment, the curator's next scheduled run picks up a syntactically-broken file and either crashes noisily (good) or — worse — parses partially and starts enforcing constraints you didn't intend. The `.wip` suffix is deliberately not read by `curator.py`; the loader whitelists only `curator.yaml`.

Rules for the actual edit:

- **One axis per commit.** If you're rebalancing phoneme targets *and* loosening a duration constraint *and* adding a new cross-axis rule, do those in three separate rounds through this runbook. Compound edits make the diff report unreadable and hide interactions.
- **Never delete a bucket.** Set its `weight` to `0.0` and its `min_count` to `0`. Deletion breaks historical reports; zeroing preserves them.
- **Comment your intent inline.** A future-you (or a future me) reading this file six months from now will not remember why the `/θ/` target dropped from `0.03` to `0.018`. Write it down next to the number.

Example of a well-annotated edit:

```yaml
phoneme_targets:
  # 2026-09-21 lo: dropped from 0.03 -> 0.018 after speaker
  # profile shifted toward American English; /θ/ overrepresented
  # relative to production script corpus. Revisit after next
  # voice LoRA training cycle.
  "θ": 0.018
```

---

### Step 3 — Lint the scratch copy

```powershell
python .\curator.py --config .\config\curator.yaml.wip --lint-only
```

`--lint-only` runs the schema validator and the internal consistency checks (weights sum to ≤ 1.0 per axis, no negative min_counts, no cross-axis rule referencing a nonexistent bucket) but does **not** touch `phrase_bank.jsonl`. Exit code semantics:

| Exit | Meaning | Action |
| --- | --- | --- |
| 0 | Schema valid, constraints internally consistent | Proceed to Step 4 |
| 10 | YAML syntax error | Fix in editor, re-lint |
| 11 | Schema validation failure (unknown field, wrong type) | Read stderr, fix, re-lint |
| 12 | Weight sum violation | Rebalance the axis, re-lint |
| 13 | Cross-axis rule references missing bucket | Either add the bucket or remove the rule |
| 14 | Numerical constraint impossible on its face (e.g. `min_count > max_count`) | Fix the inequality |

Exit 10 through 14 are all "the file is malformed" — none of them tell you whether the constraints are *satisfiable against the current corpus*. That's Step 4.

---

### Step 4 — Dry-run against the live corpus

```powershell
python .\curator.py --config .\config\curator.yaml.wip --dry-run --report-out ".\reports\post-edit.$stamp.json"
```

Read `post-edit.$stamp.json` from top to bottom. The fields to scrutinize, in order:

1. **`feasibility.status`** — must be `"feasible"`. If it's `"infeasible"`, the report tells you which constraint set produced the empty solution space; either loosen a bound or reduce a `min_count`.
2. **`feasibility.slack_min`** — the tightest satisfied constraint's slack. If this is under `0.02` (2% headroom), you've built a fragile config that will flip to infeasible the moment you promote a batch that doesn't hit that bucket. Loosen.
3. **`churn.phrases_ejected`** vs. **`churn.phrases_admitted`** — the diff between pre- and post-edit selection. Anything over 15% churn deserves an explicit "yes I meant that" moment. Anything over 40% means you're not tuning, you're rebuilding, and you should be doing that through `curator.py --rebuild` with a fresh seed, not through a `curator.yaml` edit.
4. **`bucket_deltas`** — per-bucket count changes. Scan for buckets that dropped by more than half; those are almost always accidental casualties of a cross-axis rule tightening upstream.
5. **`warnings[]`** — anything the curator flagged as suspicious but not fatal. Read every one. The curator's "suspicious" heuristics are conservative; if it complained, there's a real reason.

Diff the two reports side by side:

```powershell
python .\tools\diff_curator_reports.py `
    --before ".\reports\pre-edit.$stamp.json" `
    --after  ".\reports\post-edit.$stamp.json" `
    --out    ".\reports\diff.$stamp.md"
```

The Markdown diff is the artifact you paste into the commit message. It's also the artifact you'll reach for during rollback if this edit turns out to be wrong two weeks from now.

---

### Step 5 — Promote the scratch copy

Only after Steps 3 and 4 come back clean, and only after you've actually *read* the diff:

```powershell
Move-Item .\config\curator.yaml.wip .\config\curator.yaml -Force
python .\curator.py --seal-config
```

`--seal-config` writes a SHA-256 of the final `curator.yaml` into `curator.lock.json` alongside a timestamp and the operator identity from `$env:USERNAME`. Every subsequent `curator.py` run verifies that hash before it will read the config; a hand-edit that bypasses this runbook will trip the mismatch check and refuse to run until someone acknowledges the drift by re-running `--seal-config`. It's not security, it's a tripwire, and the tripwire has caught me twice.

---

### Step 6 — Observe the first live run

The next scheduled `curator.py` execution — the real one, not `--dry-run` — is where reality intrudes. Watch it:

```powershell
Get-Content .\logs\curator.log -Wait -Tail 50
```

What you're looking for in the tail:

- `selection.converged_in` — should be within 20% of the pre-edit value. A sudden jump from 340 iterations to 2100 means the solver is thrashing against a newly-tight constraint.
- `selection.rejected_phrases_reason_histogram` — the top rejection reason should still be the same category as before. If "phoneme overrepresentation" was your #1 rejection reason and is now #4, behind "duration out of range," you've unintentionally made duration the binding constraint. Sometimes that's fine. Sometimes it means the LoRA training loop is about to see a duration distribution it wasn't tuned for.
- `checksum.phrase_bank_post` — the new tail hash of `phrase_bank.jsonl`. Copy it into the commit message.

---

### Step 7 — Commit the config change

Not to a real VCS in this project — the workshop is single-operator — but to the `config/_history/` audit trail:

```powershell
$msg = Read-Host "One-line description of the edit"
$hash = (Get-FileHash .\config\curator.yaml -Algorithm SHA256).Hash
$entry = @{
    ts       = (Get-Date).ToUniversalTime().ToString("o")
    operator = $env:USERNAME
    hash     = $hash
    message  = $msg
    diff     = ".\reports\diff.$stamp.md"
    backup   = ".\config\_backups\curator.yaml.$stamp.bak"
} | ConvertTo-Json -Compress
Add-Content .\config\_history\curator.history.jsonl $entry
```

That JSONL is the paper trail. When someone (usually me, three months later) asks "when did the /θ/ target change and why," the answer is one `Select-String` away.

---

### Rollback

If Step 6 shows something wrong, or if the *next* nightly run flags a downstream anomaly that traces back to this edit:

```powershell
Copy-Item ".\config\_backups\curator.yaml.$stamp.bak" .\config\curator.yaml -Force
python .\curator.py --seal-config
python .\curator.py --rebuild --from-snapshot ".\snapshots\phrase_bank.$stamp.jsonl.zst"
```

The `--rebuild` path is the important one. Simply reverting `curator.yaml` doesn't unwind the phrase selections the bad config made; you have to reconstitute the phrase bank from its pre-edit snapshot, then let the reverted curator re-run selection from that clean base. Snapshots live in `.\snapshots\` and are rotated by the same GFS scheme as the ledger backups (7 daily, 8 weekly, 12 monthly).

### Failure Modes Table

| Failure | Symptom | Recovery |
| --- | --- | --- |
| Edited `curator.yaml` directly, no backup | No `.bak` file, `curator.log` shows unexpected selections | Restore from last daily snapshot in `snapshots/daily/`, replay journal from that timestamp |
| Skipped `--lint-only`, promoted broken YAML | Next `curator.py` run crashes with `yaml.scanner.ScannerError` | Move `.wip` back or restore backup; the crash prevented any corpus mutation, so no rebuild needed |
| Skipped `--dry-run`, promoted infeasible config | `curator.py` logs `feasibility.status: infeasible` and exits nonzero; corpus untouched | Restore backup, re-seal |
| Passed dry-run, failed live | Live run logs `selection.converged_in` blowing past `max_iters` | Rollback per above; re-run dry-run with `--exhaustive` flag to catch what the sampled dry-run missed |
| Forgot `--seal-config` after promotion | Next run refuses to start with `curator.lock.json mismatch` | Run `curator.py --seal-config`; investigate whether the mismatch is your edit or an unauthorized change |
| Concurrent edit by another operator | Two `.wip` files present, or `curator.history.jsonl` shows recent entry from a different `$env:USERNAME` | Stop, reconcile with the other operator, rebase your edit onto theirs |

### Anti-patterns — do not do these

- **Editing `curator.yaml` from inside a Jupyter notebook cell.** Notebooks silently retain stale state; the file on disk and the file you *think* you edited can diverge for hours before you notice.
- **Chaining edits without running the pipeline between them.** Each edit's effects compound in ways the individual dry-run reports won't reveal. One edit per runbook cycle.
- **Copying `curator.yaml` from another workshop instance.** Even if the schemas match, the constraint tuning is corpus-specific. A config that produces a balanced bank on one corpus produces junk on another.
- **Using version control tools as a substitute for this runbook.** Git can tell you *what* changed. It cannot tell you whether the change is feasible against the current corpus, and that's the only question that matters.
